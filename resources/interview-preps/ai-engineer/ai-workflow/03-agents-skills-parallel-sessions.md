## 1. Step-by-Step: How I Use Rules, Skills, and Plugins Without Context Bloat

When interviewers ask how you organize your AI customizations, explain this **3-layer hierarchy** designed to keep the context window small and accurate:

- **Layer 1 — Rules (`CLAUDE.md` / `AGENTS.md` — Always Loaded, Kept Tiny):**
  - These load into every single session automatically.
  - I keep them very short (under 50 lines): project structure, strict architectural rules, and exact terminal commands to run tests and type checks.
- **Layer 2 — Skills (`SKILL.md` — Loaded On-Demand Only When Needed):**
  - If you put 10 long playbooks into your global rules, you waste thousands of tokens on every prompt and degrade the model's attention.
  - Instead, I package specialized workflows as **Skills**. At startup, the agent only sees a 1-sentence description of each skill. When I ask the agent to perform that specific workflow—such as analyzing a `.har` network capture or scaffolding a new API connector—it loads the full `SKILL.md` instructions on demand.
- **Layer 3 — Plugins & MCP Servers (External Tool Access):**
  - Plugins bundle related skills, slash commands, and MCP tool servers (such as browser inspection, database schema inspection, or documentation lookup) into a single toggleable unit.
  - I only enable the plugins required for the active project so the agent's tool list stays lean.

## 2. Step-by-Step: How I Use Subagents to Prevent Context Degradation

When working on complex integrations or analyzing large payloads, raw data such as `.har` network dumps or API traces can be 10,000+ lines long:

- **Step 1 — Never Feed Raw Dumps to the Main Builder Agent:**
  - If the main coding agent reads a 10,000-line log or network trace, its context window fills up with noise and it starts forgetting earlier architectural rules.
- **Step 2 — Spawn a Read-Only Research Subagent:**
  - I delegate the heavy inspection to a dedicated read-only **Research Subagent**.
  - The subagent scans the giant `.har` file or codebase in its own isolated context window and returns only a concise 15-line summary (exact endpoint URL, required headers, and JSON response shape) back to the main agent.
- **Step 3 — Main Agent Implements Cleanly:**
  - The main agent stays fast, cheap, and focused strictly on implementing the feature with a clean context window.

## 3. Step-by-Step: How I Run Agent Sessions in Parallel (Without Collisions)

Explain that you use **two levels of parallelism** depending on the scope of the work—and you can point directly to the `multi-agent-worktree-orchestrator` prototype on your laptop:

### Level A: Daily Feature Development (2–3 Parallel Sessions)
- **The Golden Rule:** Two agents **never** edit the same file at the same time.
- **Session 1 (Builder Agent):** Implements the connector or service logic.
- **Session 2 (Test & Fixture Agent):** Builds offline mock payloads and edge-case test suites in a separate test file.
- **Session 3 (Research / Docs Agent):** Investigates third-party API payloads or updates state documentation.

### Level B: High-Scale Parallel Orchestration (16 Concurrent Agents with Git Worktrees)
If you need to update or scaffold 16 modules at once, running 16 agents in one folder will corrupt files and crash Git with `.git/index.lock` errors. Here is the **4-step architecture** I use (which I built into the prototype folder on my laptop):

- **Step 1 — Isolated Git Worktrees (`.worktrees/agent-01` .. `.worktrees/agent-16`):**
  - Instead of cloning the repo 16 times or spinning up 16 heavy Docker containers, I programmatically provision 16 **Git worktrees**, each on its own branch (`feature/agent-01` .. `feature/agent-16`).
  - Each agent gets its own physical folder and independent Git index while sharing the single `.git` object database and root dependencies in milliseconds.
- **Step 2 — Disjoint File Ownership:**
  - The central supervisor assigns each agent a separate module file so there are zero semantic file conflicts. Shared index files are generated by the supervisor after all workers finish.
- **Step 3 — 4-Slot Token-Bucket Rate Limiter (OpenRouter / Headless `claude -p`):**
  - Firing 16 LLM streams at once triggers `429 Too Many Requests` on APIs.
  - I gate all 16 tasks through a **4-slot concurrency semaphore and token bucket** (with exponential backoff + jitter on 429s). As soon as an agent finishes generating text, it immediately releases its API slot before running local tests.
- **Step 4 — Parallel Validation Gate, Sequential Merge Queue:**
  - Every worktree runs static type checking and unit tests **in parallel** inside its own folder.
  - Passing branches enter a **FIFO sequential merge queue** (one branch at a time) to rebase and merge onto `main` safely without ever colliding on `.git/index.lock`.
